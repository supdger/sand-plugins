# SandWorkflow 工作流用户使用文档

> 适用版本：`sandworkflow` 1.0.7
> 适用平台：SandAdmin 6.x

SandWorkflow 工作流用于在 SandAdmin 中配置审批流程、发起审批、处理待办，并留存每一次流转的完整记录。

## 1. 使用角色

| 角色 | 主要工作 |
| --- | --- |
| 系统管理员 | 安装或升级插件、分配菜单和按钮权限、维护系统用户。 |
| 流程管理员 | 创建流程分组，配置、发布、调整流程定义，查看流程数据。 |
| 流程发起人 | 选择已发布流程，填写标题和表单数据，发起并按需撤销流程。 |
| 审批人 | 在待办中心查看分配给自己的任务，并通过或拒绝。 |

同一用户可以同时拥有多个角色。审批人必须是 SandAdmin 中已存在且启用的用户。

## 2. 安装与升级

### 2.1 新安装

1. 使用 SandAdmin 的插件安装功能安装与当前插件版本一致的发行包。
2. 安装完成后刷新后台菜单；若服务启用了路由或配置缓存，请按宿主项目的运维方式重载服务。
3. 在角色权限中为管理员授予“SandWorkflow 工作流”菜单及相应按钮权限。
4. 以拥有流程管理权限的账号登录，确认左侧出现“SandWorkflow 工作流”。

安装程序会创建以 `sand_workflow_` 开头的工作流数据表，并导入工作流菜单与权限。

### 2.2 从旧版 SaiWorkflow 升级

如果宿主库中仍使用旧版 `sa_workflow_*` 表，使用本插件的升级机制执行 `update.sql`。升级会将旧表改名为 `sand_workflow_*`，并同步菜单、路由标识和权限标识至 `sandworkflow`。

升级前应完成数据库备份；升级后请检查：

1. 历史流程定义和流程实例仍可查询。
2. 角色已重新拥有 `sandworkflow:*` 权限。
3. 菜单组件路径已指向 `/plugin/sandworkflow/...`。

> 不要在同一个宿主中同时启用旧 `saiworkflow` 路由与新 `sandworkflow` 路由，以免同名接口重复注册。

## 3. 菜单与权限

工作流菜单由以下模块组成：

| 菜单 | 用途 | 建议授权对象 |
| --- | --- | --- |
| 流程中心 / 发起审批 | 选择已发布流程并发起实例。 | 需要发起流程的业务用户。 |
| 流程中心 / 待我处理 | 查看、通过或拒绝本人待办。 | 审批人。 |
| 流程中心 / 我发起的 | 查看自己发起的流程；审批中且允许撤销的流程可撤销。 | 流程发起人。 |
| 流程中心 / 我已处理 | 查看本人已完成的审批记录。 | 审批人。 |
| 流程管理 / 流程分组 | 对流程分类。 | 流程管理员。 |
| 流程管理 / 流程定义 | 新建、发布、编辑、查看版本、删除流程。 | 流程管理员。 |
| 流程数据 / 流程实例 | 查询全部流程实例及其详情。 | 流程管理员、审计人员。 |

管理员应遵循最小权限原则：普通用户无需获得流程定义和全量流程数据权限；审批人仅需被配置为流程节点处理人，并拥有待办菜单权限。

## 4. 首次配置流程

### 4.1 创建流程分组

进入 **SandWorkflow 工作流 → 流程管理 → 流程分组**，创建分组，例如“行政审批”“费用报销”或“项目管理”。

分组仅用于归类和筛选；流程能否发起由流程定义的发布状态决定。

### 4.2 创建并发布流程定义

进入 **流程管理 → 流程定义**，点击“新增流程”，填写：

- **流程名称**：业务人员可理解的名称，例如“费用报销审批”。
- **流程分组**：可选，建议选择已建立的分组。
- **说明**：描述适用范围、提交流程或业务规则。
- **设计方式**：常规场景使用“顺序审批”；复杂流程可使用“高级 JSON”。

在“顺序审批”模式中，点击“添加审批节点”，并为每个节点设置：

- 节点名称；
- 一个或多个审批人；
- 审批方式。

至少配置一个审批节点后，点击“发布”。每次发布都会产生新的流程版本；已发起的实例保留其发起时的版本快照，不会因后续编辑而改变历史流转规则。

### 4.3 审批方式说明

| 方式 | 行为 | 适用示例 |
| --- | --- | --- |
| 单人 | 指定一名处理人完成即可进入下一节点。 | 部门负责人审批。 |
| 会签 | 节点内所有处理人都通过后，才进入下一节点。任一人拒绝则流程结束。 | 多部门共同确认。 |
| 或签 | 节点内任一处理人通过即可进入下一节点，其余待办自动跳过。任一人拒绝则流程结束。 | 多位可任选其一处理。 |
| 依次审批 | 多名处理人按配置顺序逐一处理；前一位通过后，下一位才会收到待办。任一人拒绝则流程结束。 | 组长、部门负责人、总经理逐级审批。 |

### 4.4 配置条件分流（可选）

在顺序审批编辑器中点击“启用条件分流”，可根据发起时填写的表单字段进入不同分支。

例如，报销流程可用字段 `amount`：

- `amount` 大于 `5000`：进入“总经理审批”；
- 默认分支：进入“财务审批”。

填写条件时，请保证字段名与发起时 **表单 JSON** 内的键完全一致。默认分支必须保留并放在最后，用于接住不满足任何条件的情况。

### 4.5 高级 JSON 模式

高级 JSON 面向熟悉流程结构的管理员。提交时系统会校验：

1. 流程必须从发起节点开始；
2. 至少包含一个审批或办理节点；
3. 审批/办理节点必须配置处理人；
4. 审批方式必须是支持的类型；
5. 条件网关至少有两个分支，且默认分支位于最后。

如果没有维护 JSON 结构的经验，建议始终使用可视化的“顺序审批”模式。

## 5. 发起流程

1. 进入 **流程中心 → 发起审批**。
2. 找到目标流程，点击“发起”。只有已发布且启用的流程会出现在这里。
3. 填写**审批标题**，例如“张三 7 月差旅报销”。
4. 在**表单 JSON**中填写业务数据；不需要业务字段时可保留 `{}`。
5. 点击“发起”。

表单 JSON 示例：

```json
{
  "applicant": "张三",
  "amount": 6800,
  "reason": "客户现场差旅"
}
```

发起成功后，系统会创建首个待办任务。重复点击提交不会重复创建同一请求的流程实例。

## 6. 审批与撤销

### 6.1 处理待办

1. 进入 **流程中心 → 待我处理**。
2. 点击“详情”，查看发起表单、审批节点、每位处理人的状态及流转记录。
3. 点击“通过”或“拒绝”，可填写处理意见后确认。

拒绝会结束当前流程，流程状态变为“已拒绝”。通过后，系统会按当前节点的审批方式推进到下一节点或结束流程。

### 6.2 查看已办

在 **流程中心 → 我已处理** 中可查询本人已通过或拒绝的任务，并通过“详情”查看完整流转记录。

### 6.3 撤销自己发起的流程

在 **流程中心 → 我发起的** 中，只有处于“审批中”的流程才会显示“撤销”。撤销后：

- 流程状态变为“已撤销”；
- 当前未处理任务和处理人记录会被标记为已跳过；
- 撤销操作会写入流转记录；
- 撤销无法恢复。

如果系统提示“不允许撤销”，说明该流程定义未开启撤销能力或当前流程已结束。

## 7. 查看流程详情与审计

流程管理员可在 **流程数据 → 流程实例** 查看全部实例。详情侧栏会展示：

- 审批标题、当前节点和流程状态；
- 发起时保存的表单 JSON；
- 各审批节点、审批方式、处理人及处理状态；
- 发起、通过、拒绝、撤销等流转记录和处理意见。

状态含义如下：

| 流程状态 | 含义 |
| --- | --- |
| 审批中 | 仍有待处理节点。 |
| 已通过 | 所有必经节点已通过。 |
| 已拒绝 | 任一处理人执行了拒绝。 |
| 已撤销 | 发起人在流程结束前执行了撤销。 |

## 8. 常见问题

### 看不到“发起”按钮或目标流程

检查流程是否已经发布且处于启用状态，并确认当前用户拥有“发起审批”菜单权限。

### 审批人看不到待办

检查该用户是否被配置为当前节点的审批人、账号是否启用，以及是否拥有“待我处理”菜单权限。对于“依次审批”，后续审批人会在前一位通过后才看到待办。

### 条件分流没有进入预期分支

检查发起表单 JSON 的字段名、数据类型和比较值。字段 `amount` 与 `Amount` 是不同字段；没有匹配条件时，流程会进入最后的默认分支。

### 修改流程后，历史实例没有变化

这是正常行为。实例会保存发起时的流程版本快照，避免历史审批在规则变更后发生歧义。可在流程定义列表中点击“版本”查看每次发布的定义。

### 误操作了通过或拒绝

已处理任务不能再次修改。建议在提交前填写明确的处理意见；需要业务补救时，应由管理员按组织流程另行发起新的审批。

## 9. 上线前检查清单

- [ ] 管理员已完成插件安装或升级，并刷新菜单/重载服务。
- [ ] 已为流程管理员、发起人、审批人分配最小必要权限。
- [ ] 已创建至少一个分组和一条已发布流程。
- [ ] 已用不同账号验证发起、待办、通过、拒绝、撤销和详情查看。
- [ ] 已确认条件分流字段与业务表单 JSON 字段一致。
- [ ] 已完成生产数据库备份，并保留升级记录。

---

如需扩展业务表单、组织角色规则或对接外部系统，请由开发人员在 SandWorkflow 工作流的流程核心之外实现业务适配，避免直接修改已发布流程实例的历史数据。
