# SandIAM 授权与数据范围契约（IAM-04，v0.1）

> 状态：**已冻结、已实现并验收**。本文件补充 [P0 契约](sand-iam-p0-contract.md)，只定义通用授权与范围能力；不定义任何接入应用的业务资源、业务状态或数据表。

## 1. 权威与调用边界

- SandIAM 是 identity、role、resource、policy、管理员组织委派和 access audit 的权威；业务应用仍是其业务实体和最终状态机的权威。
- 业务应用必须在列表、详情、创建、更新、删除、导出与批量操作前调用 `PolicyAuthorizer`；对单条业务实体必须再调用 `assertScope`。SandIAM **不**跨库查询、更新或删除业务表。
- 后台管理者不是应用 identity。后台组织范围由 `sand_iam_admin_organization_grant` 表显式授予；宿主 `is_super=1` 仅在 SandIAM 管理面拥有全局范围。

## 2. 新增 SandIAM 迁移对象

`sand_iam_admin_organization_grant`：

| 字段 | 规则 |
| --- | --- |
| `id` | `bigint GENERATED BY DEFAULT AS IDENTITY` 主键 |
| `admin_user_id` | 宿主 SandAdmin 管理员 ID；不建立跨插件 FK，运行时以宿主已登录身份复核 |
| `organization_id` | FK `sand_iam_organization(id)`，`ON DELETE RESTRICT` |
| `status` | `1` 已授予、`2` 已撤销 |
| 审计字段 | `created_by`、`updated_by`、`create_time`、`update_time`、`delete_time` |

唯一约束为 `(admin_user_id, organization_id)`。该表仅保存 SandIAM 委派事实，绝不复制 `sa_system_user`。

## 3. PolicyAuthorizer 契约

```text
authorize(application_id, identity_id, resource_code, action, operation, attributes, request_id)
  -> { allowed, code, policy_ids, scope }

assertScope(scope, attributes, operation, request_id)
  -> allowed or SAND_IAM_RESOURCE_SCOPE_DENIED
```

- `operation` 固定为 `list`、`read`、`create`、`update`、`delete`、`export`、`batch` 之一；未知值为 `SAND_IAM_POLICY_DENIED`。
- 有效角色是直接授予身份的角色与身份处于启用成员关系的用户组角色之并集，并按 role ID 去重。用户组、成员关系、用户组角色关系和 role 任一停用，或任何一端不属于当前 application 时，该来源必须 fail-closed。
- `sand_iam_identity_group_role` 以 `(identity_group_id, role_id)` 唯一，并以 `(identity_group_id, application_id)` 与 `(role_id, application_id)` 外键保证两端同属一个接入应用；接入应用由其 `organization_id` 唯一确定客户主体边界。
- identity、resource 和所有命中的 role 必须启用且属于同一 application；resource 与 policy 的 application 必须一致。
- 当前角色判定每次从 PostgreSQL 读取有效关系，不使用独立授权缓存；用户组角色的授予、撤销和审计记录在一个事务中，审计失败不得留下关系变更。
- 仅 `state=published`、`status=1` 的 policy 可参与判定。按 `priority` 升序；同一 priority 时 `deny` 优先。第一个条件匹配的策略决定 allow/deny。
- 没有命中策略一律拒绝 `SAND_IAM_POLICY_DENIED`，绝不以空范围或后台 `created_by` 放行。
- 每次允许和拒绝都写 `sand_iam_audit_log`，不得写入业务正文、完整身份 token 或明文凭证。角色策略命中记录其来源（直接角色或具体用户组）；策略模拟以只读方式返回同一来源说明。

## 4. 条件与范围 JSON 语法

P0 只接受对象；未知键、嵌套对象或非标量事实均拒绝为 `SAND_IAM_POLICY_DENIED`。

```json
{
  "condition": {
    "equals": { "record_state": "open" },
    "in": { "user_type": ["employee", "application_admin"] }
  },
  "scope": {
    "equals": { "organization_id": 42 },
    "in": { "owner_identity_id": [101, 102] }
  }
}
```

- `condition` 对本次调用的 `attributes` 求值；为空对象代表无额外条件。
- `scope` 是返回给业务应用的可审计限制描述。`list`、`export`、`batch` 必须将其编译为自身查询条件；`read`、`create`、`update`、`delete` 必须以目标实体实际属性调用 `assertScope`。
- `equals` 的值只能为 string、int、bool 或 null；`in` 的值是同类型标量数组。任何不匹配均为范围拒绝，不能降级为全量可见。

## 5. 管理面范围

- organization/application/environment/client/credential/grant/identity/role/resource/policy/audit 的列表、详情、保存、更新、停用、轮换、撤销、导出和批量操作，都必须先解析当前后台管理员允许的 organization 集合。
- `service` 与 `service_action` 是平台全局目录，只允许宿主超级管理员操作；委派管理员不能借此扩大可调用服务。
- 跨 organization 一律返回 `SAND_IAM_ORGANIZATION_ACCESS_DENIED` 并记录 audit；空范围不是空列表，而是拒绝。

## 6. IAM-04 验收矩阵

1. 两个 organization 的 identity/resource/policy：一方的 policy 不可授权另一方 identity。
2. 同一 identity 的 allow、同优先级 deny、无 policy、条件不匹配均产生正确决定和审计。
3. `scope` 对 list/read/create/update/delete/export/batch 的调用约束一致；不允许仅列表过滤。
4. 委派后台管理员只能看到和变更已授予 organization；全局 service 目录被拒绝。
5. 所有测试在 PostgreSQL 回滚事务中运行，确认审计可见且无测试残留。

## 7. 实现验收记录

- PostgreSQL `0.1.1` 迁移在隔离库和 SandAdmin 验收库均确认创建 `sand_iam_admin_organization_grant`。
- 真实验收宿主对 `list/read/create/update/delete/export/batch` 七个 operation 均返回 allow；同优先级 deny、无策略、条件不匹配和范围不匹配均返回稳定拒绝，写入 6 条审计后回滚，`residual_org=0`。
- 委派管理员对另一 organization 返回 `SAND_IAM_ORGANIZATION_ACCESS_DENIED`，并写入 1 条拒绝审计；七 operation 的允许调用写入 7 条审计后回滚，`residual_org=0`。
- 身份源绑定、用户类型和身份—用户类型关系均在真实验收库回滚事务中创建成功，且关系两端的 application 一致，`residual_org=0`。
- 验收宿主已更名为 SandAdmin。SandIAM 源码引用 `plugin\\sandadmin`；过渡期在旧命名空间无法解析时按需双向别名，不改动宿主核心目录。正式标签发布后删除别名。
