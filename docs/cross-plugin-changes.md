# 跨插件变更论证

本规则适用于插件开发引起的其他插件、`sand-core`、`sand-package` 改造，也适用于由 SandAdmin 或消费工作区发起的同类变更。`sand_plugins` 负责论证与提供方边界审查；实现仍在目标组件的权威源码中完成。

## 先验证使用方式

先核对目标版本的公开 API、扩展点、配置和已有消费示例，用真实业务场景做最小验证。调用方的业务状态、重试、数据解释和适配代码归调用方；不能因为接入方便、缺少 HTTP 包装或已经开发完成，就认定需要改提供方。既有方式可满足需求时，在消费插件内实现，不触发跨插件改造。

## 可接受的依据

需要修改提供方时，至少证明以下一项，并保持提供方领域边界：

- **通用性**：抽象属于提供方职责，明确实际受益的不同消费场景，验证方案不绑定调用方名称、协议、业务数据或专用权限。多个场景只是证据，不允许复制业务代码后改名冒充通用能力。
- **必要性**：已确认的调用方自身功能，在目标版本公开 API、扩展点、配置及消费端适配下无法实现；给出最小失败复现、实际结果和不能采用替代方案的原因。只修改造成阻碍的最小提供方契约，专用业务仍由调用方承担。

必要性不要求已有多个消费者，通用性也不要求证明所有替代方案都不可行。两条路径都不能以臆测、未运行的原型或成功绕过代替关键证据。

## 在 sand_plugins 形成结论

在 `sand_plugins` 当前相关 OpenSpec 的 design/tasks 中记录，确属新范围时建立相关 change；其他仓库引用该记录。记录须包含：

1. 真实需求、调用方与提供方、锁定版本或源码 revision、源码所有者；
2. 现有能力与最小验证结果、替代方案及取舍，通用性或必要性证据；
3. 最小变更范围、API 与依赖方向、权限及数据归属、安装/升级/卸载与兼容影响；
4. 验收与回滚方式、未验证项、审查者和通过/退回结论。

由 `sand_plugins` 负责方按现行编排规则安排未参与实现的审查者核对证据，提出方不能自行评审放行。记录通过结论后才能修改提供方；缺失证据、复现失败或无法核实关键结果时补充验证，保持未通过状态，并继续可独立完成的消费端工作。已通过结论在相同目标和边界内复用；新增目标、契约或影响范围时补充论证，不按补丁次数重新审批。

用户明确授权的回滚与恢复可依据已确认的恢复范围执行，不要求先替被撤回方案补做通用性论证；若恢复过程中新增能力或扩大提供方职责，新增部分仍须论证。

本规则属于开发与审查约束，不宣称已有 Hook 或运行时强制拦截；不替代用户授权，也不自动授权数据库迁移、服务操作、宿主同步、提交、推送或发布。
